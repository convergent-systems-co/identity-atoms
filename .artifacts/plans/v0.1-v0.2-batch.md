## 2. Rationale — Alternatives Table

| Alternative | Pros | Cons | Verdict |
|---|---|---|---|
| **A. Per-method schema files (one schema per auth-method) as sketched in brief step 6 | Lets each schema diverge freely; smaller per-file scope. | Fragments the ecosystem-wide pattern; doubles maintenance; no sibling catalog uses this shape; the `type`-discriminated union is the standard `*-atoms` convention captured in `atoms-spec/v1`. | Rejected |

The brief said the partition examples were illustrative ("Typical: 3-5 coders. … Example partition for v0.1"); I am applying that guidance rather than its surface form.

## 3. Scope

### Create
- `scripts/validate.py` — JSON-Schema validator walking `atoms/<type>/*.json` and `identities/<id>/definition.json`; checks (a) JSON Schema validation, (b) `id` matches filename stem, (c) `type` matches parent dir, (d) every `ref` inside compositions resolves to a known atom or schema. Plus `rules/*.py` import-smoke pass. Exit non-zero on any failure.
- `project.yaml` — minimal config naming `python3 scripts/validate.py && pytest -v` as `tooling.test_command`.
- `schemas/atom-v1.json` — discriminated-union schema for the four atom types: `auth-method`, `claim-type`, `trust-framework`, `key-cert-type`.
- `schemas/composition-v1.json` — schema for `identities/*/definition.json` (the v0.1 persona-template shape).
- `schemas/federated-composition-v1.json` — extends composition-v1 with multi-IdP federation fields (v0.2, Task #9).
- `atoms/auth-method/oauth2-1.json`, `oidc.json`, `saml.json`, `webauthn.json`, `ssh-key.json`, `mtls.json` — six seed `auth-method` atoms (Task #5).
- `atoms/claim-type/sub.json`, `iss.json`, `aud.json` — three standard claim types (supports persona template).
- `atoms/trust-framework/corp-ca.json`, `web-of-trust.json` — two seed trust frameworks.
- `atoms/key-cert-type/ed25519.json`, `rsa-2048.json`, `x509.json` — three seed key/cert types.
- `identities/aish-work-persona/definition.json` — the canonical persona template (Task #3, exemplifies #6).
- `identities/federated-corp-to-vendor/definition.json` — federated example (Task #9, #11).
- `rules/key_rotation.py` — pure-Python rule evaluator: given a key atom + a `last_rotated` ISO-8601 timestamp + current time, returns `{status: ok|grace|expired, age_days, next_due}` (Task #7).
- `rules/trust_chain.py` — pure-Python validator: given a chain of `key-cert-type` refs, returns `{valid: bool, broken_at: int|null, reason: str}` (Task #10).
- `docs/persona-loader-integration.md` — narrative + worked example showing how aish v0.3 reads a composition (Task #6).
- `docs/cross-org-bridging.md` — narrative explaining the federated example (Task #11).
- `tests/` (pytest):
  - `tests/test_atoms_validate.py` — every atom passes schema + id/type/path invariants.
  - `tests/test_compositions.py` — every composition validates; every `ref` resolves.
  - `tests/test_persona_template.py` — `aish-work-persona` round-trips through the schema and exposes the loader-contract fields documented in `docs/persona-loader-integration.md`.
  - `tests/rules/test_key_rotation.py` — table-driven cases: fresh key → ok; expired → expired; in grace window → grace; missing `last_rotated` → expired.
  - `tests/rules/test_trust_chain.py` — valid chain → ok; broken middle → broken_at index; empty chain → invalid.
  - `tests/test_federated_composition.py` — federated schema accepts multi-IdP; cross-org example resolves; trust-chain rule runs over the chain in the composition.

## 5. Testing strategy

- **Static / schema** — every `atoms/**/*.json` and `identities/**/definition.json` must validate against its declared schema. `scripts/validate.py` is the gate.
- **Behavior** — pytest suite covers: (a) every atom validates, (b) every composition resolves its refs, (c) `rules/key_rotation.py` returns correct verdict on table of fixtures, (d) `rules/trust_chain.py` returns correct verdict on table of fixtures, (e) federated composition example resolves end-to-end.
- **Integration contract** — `tests/test_persona_template.py` asserts the persona-template exposes the exact field set documented in `docs/persona-loader-integration.md`, so a drift between doc and data fails CI (Task #6 acceptance).
- **No mocks** for schema/file/rule logic. The only allowed mock is `datetime.now()` in key-rotation tests (rotation is time-dependent).

## 6. Risk assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Schema discriminated-union (`allOf` + `if/then`) escapes jsonschema 4.25 validation in subtle ways | Med | Tester runs adversarial pass; one negative-case test (`type=auth-method` missing `auth_method` block) asserts schema rejects it. |
| Two coders touch the same file by accident | Low | OWNS lists are disjoint by file path; coder prompts forbid out-of-scope edits; pre-merge tester diffs the branch. |
| Persona-loader integration doc claims an interface aish v0.3 does not have | Med | Doc + composition + test agree by construction; if aish later differs, that's an aish-side adapter, not an identity-atoms defect. Documented as assumption. |
| Federated schema bleeds into v0.1 scope | Low | Federated schema is named separately (`federated-composition-v1.json`); v0.1 personas validate against `composition-v1.json` only. |
| `gh` auth wrapper missed on a write call → operation lands under wrong identity | Med | Every write call wrapped: `GH_TOKEN="$(gh auth token --user polliard)" gh …`; PR creation rehearsed in dry-run order before fire. |

## 10. Assumptions (per Common.md U1)

- aish v0.3's persona loader will read JSON identity compositions through a key set: `id`, `version`, `auth_methods[]`, `keys[]`, `claims.required[]`, `trust_framework`. This is the contract `docs/persona-loader-integration.md` documents and `tests/test_persona_template.py` enforces. If the eventual aish v0.3 loader needs different fields, that is an aish-side adapter problem, not an identity-atoms break.
- The `ref` form `<atom-type>/<atom-id>` is the resolver convention (mirrors the GOALS.md example which used `atoms/auth-method/oidc`).
- "Cross-org identity bridging examples" (Task #11) is satisfied by one worked example + narrative doc; not by a multi-example matrix.
